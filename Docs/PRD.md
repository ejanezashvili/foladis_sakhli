# ფოლადის სახლი — დავალებების მართვის სისტემა

წყარო: `Docs/ფუნქციონალი (2).docx` (კლიენტის მოთხოვნები), მოთხოვნების რუკა — `Docs/გეგმა.md`.

## Problem
კომპანიას (50–100 მომხმარებელი, რამდენიმე ათეული დეპარტამენტი) დავალებები ერთ ადგილას არ ჰქონდა: არ ჩანდა, ვის რა აქვს გასაკეთებელი, რა ეტაპზეა, ვინ ამოწმებს შედეგს და რა ვადაგადაცილებულია. დავალება ხშირად რამდენიმე დეპარტამენტს გადის რიგრიგობით, და შემდეგმა არ იცის, როდის შეუძლია დაწყება. შვებულებების დამტკიცება და შემცვლელის დანიშვნაც ხელით ხდებოდა.

## User stories
- **US-1** როგორც თანამშრომელს, მინდა ერთ გვერდზე ვხედავდე ჩემს დავალებებს, რომ ვიცოდე, რა მაქვს გასაკეთებელი.
- **US-2** როგორც თანამშრომელს, მინდა დავალება მივიღო, დავიწყო და მოვნიშნო შესრულებულად, რომ ავტორმა იცოდეს მდგომარეობა.
- **US-3** როგორც შემმოწმებელს, მინდა შესრულებული დავალება დავადასტურო ან დავაბრუნო მიზეზით, რომ შედეგი ჩემი შემოწმების გარეშე არ დაიხუროს.
- **US-4** როგორც ავტორს, მინდა დიდი დავალება ნაბიჯებად დავყო (რიგრიგობით ან ერთდროულად), რომ თითო ნაბიჯს თავისი შემსრულებელი და ვადა ჰქონდეს.
- **US-5** როგორც ნაბიჯის შემსრულებელს, მინდა ვხედავდე, რას ველოდები და ვინ მელოდება, რომ ვიცოდე ჩემი ჯერი.
- **US-6** როგორც თანამშრომელს, მინდა დავალება შევაჩერო მიზეზით, როცა ვერ ვაგრძელებ, და შემდეგ ნაბიჯს მივცე დაწყების ნება.
- **US-7** როგორც მომლოდინე ნაბიჯის შემსრულებელს, მინდა წინა ნაბიჯის ხალხს ვთხოვო დაწყება, რომ საქმე არ გაჩერდეს.
- **US-8** როგორც ადმინისტრატორს, მინდა განვსაზღვრო, ვინ ვის დავალებებს ხედავს, რომ თანამშრომელი მხოლოდ თავის საქმეს ხედავდეს.
- **US-9** როგორც ხელმძღვანელს, მინდა ვხედავდე ვადების დაცვას და დატვირთვას, რომ დროულად ჩავერიო.
- **US-10** როგორც თანამშრომელს, მინდა შვებულება მოვითხოვო და შემცვლელი მივუთითო, რომ ჩემი საქმე არ გაჩერდეს.
- **US-11** როგორც ახალ მომხმარებელს, მინდა ვიდეო სახელმძღვანელო, რომ სისტემა დამოუკიდებლად ავითვისო.

## In scope
- დავალებები: სტადიები, მიღება, შემოწმება, დაბრუნება / შეჩერება / გაუქმება მიზეზით, მტკიცებულება, „საბოლოო პროექტი“.
- თანმიმდევრობა: ნაბიჯები, ერთ ნაბიჯში რამდენიმე დავალება, გადაადგილება, ლოდინი, დაშვება, დაწყების მოთხოვნა.
- დაფები: დეპარტამენტის დაფა, „ჩემი დავალებები“, „დადასტურებები“, „მთავარი“.
- ხილვა სიის მიხედვით, „დამატებით ხედავენ“.
- შეტყობინებები და შეხსენებები (ვადა, ვადაგადაცილება, კვირის შეჯამება), განმეორებადი დავალებები, შაბლონები.
- რეპორტები: Timeline და დატვირთვა, ვადების დაცვა, შეჩერება და გაუქმება (Excel, PDF).
- სტრუქტურა: დეპარტამენტები, რამდენიმე თანაბარი ხელმძღვანელი, ორგანიზაციული სქემა.
- შვებულება: მოთხოვნა, შემცვლელები, დამტკიცების რიგი, ბალანსი კვარტლებით, რეპორტი, სავალდებულო დღეები.
- აუდიტის ჟურნალი, ღამის ბექაპი, ქართული ინტერფეისი, ვიდეო სახელმძღვანელოები.

## Out of scope
- კონფიდენციალური დავალებები (მოხსნილია 19.0.1.176.0-ში; ჩაანაცვლა ხილვამ სიის მიხედვით).
- ნებართვა შემდეგი ნაბიჯის დასაწყებად, როცა წინა ნაბიჯი შეჩერებული **არ არის** (D-6).
- ავტომატური ტესტები და სატესტო სერვერი (D-7, D-8).
- ელფოსტით შეტყობინებები, სანამ SMTP / HTTPS არ არის გამართული (`Docs/გეგმა.md`, 4.7).
- ხელფასი, დროის აღრიცხვა (timesheet), CRM, საწყობი.

## Acceptance criteria
- **AC-1** (US-1) Given თანამშრომელი შესულია, When ხსნის „დავალებები → ჩემი დავალებები“, Then ხედავს მხოლოდ იმ დავალებებს, სადაც შემსრულებელია, პირად სვეტებში.
- **AC-2** (US-2) Given დავალება „ახალშია“, When შემსრულებელი აჭერს „მიღება“, Then სტადია ხდება „მიღებული“ და ავტორი ამას ხედავს.
- **AC-3** (US-2, US-3) Given დავალება „მიღებული“ ან „მიმდინარეა“, When შემსრულებელი აჭერს „შესრულებულია“, Then დავალება გადადის „შემოწმებაზე“ და ჩნდება შემმოწმებლის „დადასტურებებში“.
- **AC-4** (US-3) Given დავალება „შემოწმებაზეა“, When შემმოწმებელი უარყოფს, Then მიზეზი სავალდებულოა და დავალება ხდება „დაბრუნებული“.
- **AC-5** (US-3) Given დავალება „შემოწმებაზეა“, When მას ადასტურებს ვინმე, ვინც შემმოწმებელი ან ადმინისტრატორი არ არის, Then სისტემა არ უშვებს.
- **AC-6** (US-4) Given მთავარ დავალებას აქვს ნაბიჯები, When ყველა ნაბიჯი დახურული არ არის, Then მთავარი დავალება „შემოწმებაზე“ ვერ გადადის.
- **AC-7** (US-4, US-5) Given ნაბიჯს აქვს ღია წინა ნაბიჯი, When შემსრულებელი ცდილობს მის მიღებას, Then სისტემა არ უშვებს და აჩვენებს, რომელ დავალებებს ელოდება.
- **AC-8** (US-4) Given ერთ ნაბიჯში ორი დავალება დგას, When წინა ნაბიჯი დადასტურდება, Then ორივე ერთდროულად ხდება მისაღები, შემდეგი ნაბიჯი კი ელოდება ორივეს.
- **AC-9** (US-5) Given თანამშრომელი ნაბიჯის შემსრულებელია, When ხსნის ბარათზე „თანმიმდევრობა“-ს, Then ხედავს ყველა ნაბიჯს და მისი ნაბიჯები გამოყოფილია.
- **AC-10** (US-6) Given წინა ნაბიჯი შეჩერებულია და მხოლოდ ის აფერხებს შემდეგს, When მისი შემსრულებელი, პასუხისმგებელი, შემმოწმებელი ან ადმინისტრატორი აჭერს „▶ შემდეგის დაშვება“, Then შემდეგი ნაბიჯი ხდება მისაღები, შეჩერებული კი შეჩერებული რჩება.
- **AC-11** (US-6) Given დავალება შეჩერებულია, When მას აბრუნებენ სამუშაო სტადიაზე, Then ის ყოველთვის „ახალში“ ბრუნდება.
- **AC-12** (US-7) Given ნაბიჯი ელოდება წინას, When მისი შემსრულებელი აჭერს „🙋 დაწყების მოთხოვნა“, Then ყველა ღია წინა ნაბიჯის შემსრულებელს, პასუხისმგებელს და შემმოწმებელს მისდის შეტყობინება; ხელახლა გაგზავნა შეიძლება ერთი საათის შემდეგ; მთავარ დავალებაზე ღილაკი არ ჩანს.
- **AC-13** (US-8) Given თანამშრომელი დავალების მონაწილე არ არის და „დავალებების ხილვაში“ მონიშნული არ არის, When ხსნის დეპარტამენტის დაფას, Then ამ დავალებას ვერ ხედავს.
- **AC-14** (US-8) Given მომხმარებელი დავალებას მხოლოდ ხედავს („დამატებით ხედავენ“ ან ხილვის სიით), When ცდილობს მის შეცვლას, Then სისტემა არ უშვებს.
- **AC-15** (US-9) Given ხელმძღვანელი ხსნის „რეპორტინგი → ვადების დაცვა“, When ირჩევს პერიოდს, Then ხედავს დროულად და დაგვიანებით დასრულებულებს და შეუძლია Excel-ად და PDF-ად ჩამოტვირთვა.
- **AC-16** (US-10) Given თანამშრომელი ითხოვს შვებულებას შემცვლელით, When პირველი დამმტკიცებელი ადასტურებს, Then მოთხოვნა გადადის შემდეგ დამმტკიცებელზე და შემცვლელი იღებს შეტყობინებას.
- **AC-17** (US-11) Given `Docs/ვიდეო მანუალები/`, When მომხმარებელი ხსნის ვიდეოს, Then ხედავს ცოცხალი სისტემის ეკრანებს ქართული წარწერებით, სადაც წერია, ვისი ეკრანია კადრში.

## Non-functional
- ენა: ქართული ინტერფეისი (`i18n/ka`), საკუთარი მოდულების ტექსტი ქართულად წყაროშივე.
- უფლებები: თანამშრომელი ხედავს მხოლოდ თავის საქმეს; შეცვლა — მხოლოდ მონაწილეებს და დეპარტამენტის ხელმძღვანელს.
- აუდიტი: OCA `auditlog` — დავალებები, პროექტები, მომხმარებლები.
- ბექაპი: ყოველ ღამე 02:00, თვეში ერთხელ აღდგენის ტესტი.
- მოცულობა: 50–100 მომხმარებელი.
- მობილური: OCA `web_responsive`.
- კავშირი: ამჟამად HTTP (HTTPS არ არის).
