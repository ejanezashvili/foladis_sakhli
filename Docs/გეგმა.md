1. ბაზის სრული backup (pg_dump + filestore) ნებისმიერი ცვლილების წინ.
2. დომენი + HTTPS (nginx + Let's Encrypt); `proxy_mode`; `web.base.url` განახლება.
3. გამავალი ფოსტა (SMTP) და შემომავალი (საჭიროების შემთხვევაში) — შეტყობინებებისთვის აუცილებელია.
4. ქართული ენის (ka_GE) ჩატვირთვა, დროის სარტყელი Asia/Tbilisi.
5. Git რეპო ამ საქაღალდეში: `addons/` (OCA + საკუთარი), `Docs/`, დეპლოის სკრიპტი.
6. ავტომატური ღამის backup cron სერვერზე + აღდგენის ტესტი (მოთხ. 8.5).

### ეტაპი 1 — დემოს გაწმენდა
- დემო პროექტების/დავალებების/სტადიების/კონტაქტების/თანამშრომლების არქივაცია ან წაშლა; კომპანიის სახელის, ლოგოს, მისამართის შეცვლა.
- ტესტ-მომხმარებლების წაშლა/დეაქტივაცია.

### ეტაპი 2 — სამუშაო შეხვედრა კლიენტთან (საჭირო მონაცემები)
- დეპარტამენტების/ქვედანაყოფების/გუნდების სია, ხელმძღვანელები და შემცვლელები.

- როლების მატრიცა (ვინ რას ხედავს/ცვლის), კონფიდენციალური დავალებების წესები.
- ვადების შეხსენების წესები (რამდენი დღით ადრე), ესკალაციის ზღვრები, სამუშაო კალენდარი და უქმეები.
- ტერმინოლოგიის შეთანხმება ქართულად (მოთხ. 8.8).

### ეტაპი 3 — ჩაშენებული ფუნქციონალის კონფიგურაცია (კოდის გარეშე)

### ეტაპი 5 — საკუთარი მოდული `steelhouse_project` (მხოლოდ ხარვეზები)
`addons/steelhouse_project/`:
- **ველები `project.task`-ზე** (tracking=True): `responsible_id` (მთავარი პასუხისმგებელი; `user_ids` = მონაწილეები), `reviewer_id` (შემმოწმებელი), `date_start` (დაწყება), `department_id`, `location_id`/ფილიალი, `category_id`, `progress` (%), `is_confidential`, `hold_reason`/`resume_date`, `return_reason`, `cancel_reason`, `evidence_required`, `date_done`, `is_overdue`, `on_time` (stored compute — ანგარიშებისთვის), `return_count`.
- **ვიზარდები**: დაბრუნება/შეჩერება/გაუქმება მიზეზის სავალდებულო შეყვანით; დეპარტამენტზე გადაცემა (ისტორია chatter-ში).
- **წესები (constraints)**: „დასრულებულში“ გადაყვანა მხოლოდ reviewer-ს/ხელმძღვანელს; მტკიცებულების ფაილი სავალდებულოა, თუ `evidence_required`.
- **`hr.department`**: `deputy_id` (შემცვლელი) — გადატანილია ცალკე მოდულში `steelhouse_hr` (დაყენებულია).
- **დელეგირება (B)**: შვებულების დამტკიცებისას (hr.leave) დავალებები/შეტყობინებები შემცვლელზე გადამისამართება.
- **უსაფრთხოება**: ჯგუფები (თანამშრომელი / შემმოწმებელი / დეპარტამენტის ხელმძღვანელი / ხელმძღვანელობა / ადმინი), record rules: კონფიდენციალური დავალება ჩანს მხოლოდ მონაწილეებს+ხელმძღვანელს; ხელმძღვანელი ხედავს თავის დეპარტამენტს.
- **ხედები**: ფორმა/სია/კანბანი/კალენდარი/pivot ახალი ველებით, ფილტრები (ჩემი, ვადაგადაცილებული, ჩემი დეპარტამენტი, შემოწმებაზე).
- **PDF ანგარიში** (QWeb) — დეპარტამენტის/თანამშრომლის შესრულების ანგარიში.
- **ქართული თარგმანი** `i18n/ka.po`.

### ეტაპი 6 — ავტომატიზაცია (`base_automation`, საჭიროებისას საკუთარ მოდულში XML-ით)
- ახალი/გადანაწილებული დავალება → შეტყობინება (ჩაშენებულია assign-ზე).
- ვადამდე N დღით ადრე → შეხსენება (time-based trigger, `date_deadline`).
- ვადა გადაცილდა → `is_overdue` მონიშვნა + ხელმძღვანელის ინფორმირება.
- ხანგრძლივი დაგვიანება / კრიტიკული → ესკალაცია ზემდგომზე (B).
- „შემოწმებაზე“ X დღე → შეხსენება reviewer-ს.
- მიღების დადასტურება: „ახალი“-დან „მიღებული“-ში გადაყვანა შემსრულებლის მიერ (B).
- დასრულებისას → მომდევნო დავალების ავტომატური შექმნა (B; დამოკიდებულებებით/შაბლონით).
- დღიური/კვირეული შეჯამება (scheduled action + email template; ან `digest` KPI-ები) (B).

### ეტაპი 7 — ანგარიშგება და Dashboard
- Project → Reporting (pivot/graph) + `spreadsheet_dashboard`-ში ხელმძღვანელობის პანელი: სტატუსების რაოდენობა, შესრულება დეპარტამენტის/თანამშრომლის მიხედვით, დროულობის %, გეგმა vs ფაქტი, საშუალო დრო, დაბრუნებების სტატისტიკა.
- მეტრიკიდან სიაზე გადასვლა (pivot/graph drill-down — ჩაშენებულია).
- ექსპორტი XLSX/CSV (ჩაშენებული), PDF (ეტაპი 5 ანგარიში).
- ავტომატური კვირეული/თვიური ანგარიში ელფოსტით (B).

### ეტაპი 8 — მონაცემები, ტესტირება, გაშვება
1. დეპარტამენტების/თანამშრომლების/მომხმარებლების იმპორტი (Excel → Odoo Import).
2. პილოტი 1–2 დეპარტამენტზე (UAT) → შესწორებები.
3. ტრენინგი + მოკლე ქართული ინსტრუქცია როლების მიხედვით.
4. სრული გაშვება; 2FA ჩართვა ხელმძღვანელებისთვის.

**რიგითობა:** ჯერ ყველა A-მოთხოვნა (ეტაპები 0–7), B-მოთხოვნები — მეორე ტალღაში.
