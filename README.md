# ფოლადის სახლი — დავალებების მართვის სისტემა

Odoo 19 Community-ზე (Project აპლიკაცია) აწყობილი დავალებების მართვის სისტემა.

- `Docs/ფუნქციონალი (2).docx` — კლიენტის მოთხოვნები
- `Docs/გეგმა.md` — დანერგვის გეგმა ეტაპებად და მოთხოვნების რუკა
- `addons/` — საკუთარი და OCA მოდულები (მომზადების პროცესშია)

პრინციპი: ჯერ Odoo-ს ჩაშენებული ფუნქციონალი, შემდეგ OCA მოდულები, საკუთარი კოდი — მხოლოდ ხარვეზებისთვის.

## მოდული `steelhouse_project` (ჯერ არ არის დაყენებული)

დაწერილია, სერვერზე არ არის დაყენებული — ელოდება დამტკიცებას (დავალებების ეტაპი).

დამოკიდებულება: მხოლოდ `project`. დაყენება: საქაღალდე `addons/` დაემატოს Odoo-ს `addons_path`-ში → Apps → Update Apps List → „Steelhouse Project“ → Install.

რას ამატებს:
- **სტადიები** და პროექტი „ოპერატიული დავალებები“: ახალი → მიღებული → მიმდინარე → შეჩერებული → შემოწმებაზე → დაბრუნებული → დასრულებული / გაუქმებული
- **ღილაკები** დავალებაზე: მიღება, დაწყება, შემოწმებაზე გაგზავნა, დადასტურება, დაბრუნება, შეჩერება, განახლება, ვადის გადაწევის მოთხოვნა, გაუქმება
- **მთავარი პასუხისმგებელი** და **შემმოწმებელი** (ნაგულისხმევად — ვინც დავალება შექმნა)
- **ვადის გადაწევა**: თანამშრომელი ითხოვს ახალ ვადას მიზეზით, შემმოწმებელი ადასტურებს/უარყოფს; თავდაპირველი ვადა ინახება. ვადას პირდაპირ ცვლის მხოლოდ შემმოწმებელი
- **დასრულება და გაუქმება** მხოლოდ შემმოწმებელს ან პროექტის მენეჯერს შეუძლია
- **მიზეზები**: დაბრუნება, შეჩერება (+ განახლების თარიღი), გაუქმება — ინახება და ჩანს ისტორიაში
- **მტკიცებულება**: თუ მონიშნულია, შემოწმებაზე გაგზავნა ფაილის გარეშე არ შეიძლება
- **შეხსენებები** (ყოველ საათში): ვადამდე 24 სთ — შემსრულებლებს; ვადაგადაცილება — შემმოწმებელს
- **ანგარიშებისთვის**: დასრულების თარიღი, დროულად შესრულდა / თავდაპირველ ვადაში შესრულდა, გადაწევებისა და დაბრუნებების რაოდენობა
- **შაბლონები**: „მარაგების დათვლა“, „მარაგის შევსების მოთხოვნა“

## მოდული `steelhouse_hr` (დაყენებულია, ვერსია 19.0.1.2.0)

დამოკიდებულება: `hr`, `hr_org_chart`, `web_hierarchy`, `hr_holidays`.

რას ამატებს:
- დეპარტამენტზე ველი **„შემცვლელი“** (`deputy_id`, ისტორიაში იწერება) — ფორმაში, სიაში და ძიებაში (მოთხოვნა 1.2)
- **შვებულების მოთხოვნაზე ცხრილი „შემცვლელები“** (`steelhouse.leave.delegation`: დეპარტამენტი + შემცვლელი; მოთხოვნა 1.6). ხელმძღვანელს წინასწარ ევსება მის დეპარტამენტებზე დეპარტამენტის შემცვლელით; საკუთარი თავი/გამეორებული დეპარტამენტი — აკრძალულია. დავალებებზე ზემოქმედება — კომპანიის პასუხის მოლოდინში
- **დეპარტამენტების იერარქიის ხედი** (`js_class="steelhouse_department_hierarchy"`): კომპანიის ბარათი ცენტრშია; „გაშლისას“ ბარათი ადგილზე რჩება და ქვედეპარტამენტები მის ქვეშ, ცენტრში, მუქ ჩარჩოში ჩნდება (ისარი ბარათისკენ). JS/SCSS — `web.assets_backend_lazy` ბანდლში (`web_hierarchy`-ის მსგავსად)

შეზღუდვები:
- ამ ხედში ბარათის გადათრევა (drag & drop) გამორთულია — ზემდგომი დეპარტამენტი იცვლება ფორმიდან
- ერთ დონეზე ერთდროულად ერთი ბარათია გაშლილი (Odoo-ს სტანდარტული ქცევა)

სერვერზე: მოდულები დევს `/opt/odoo/custom-addons`-ში (`addons_path` — `/etc/odoo/odoo.conf`). ბაზის სარეზერვო ასლები: `/var/backups/odoo`.

## მოდული `steelhouse_task_flow` (დაყენებულია, ვერსია 19.0.1.2.1)

დამოკიდებულება: `project`. მოთხოვნები 3.1, 3.3–3.9.
- სტადიას აქვს **„სტადიის ტიპი“** (`sh_kind`): ახალი / მიღებული / მიმდინარე / შეჩერებული / შემოწმებაზე / დაბრუნებული / დასრულებული / გაუქმებული. ახალი სტადიის დამატებისას ტიპი ფორმაში უნდა მიეთითოს
- სტადიის შეცვლისას სტატუსი თავისით მიჰყვება (დასრულებული → შესრულებული, გაუქმებული → გაუქმებული, დაბრუნებული → მოთხოვნილია ცვლილებები) და პირიქით
- **შეჩერება / დაბრუნება / გაუქმება** — მხოლოდ ღილაკით, სავალდებულო მიზეზით (შეჩერებისას + განახლების თარიღი); მიზეზი ინახება და ჩანს ისტორიაში
- **„შემმოწმებელი“** (ნაგულისხმევად შემქმნელი): დასრულება, დაბრუნება, გაუქმება — მხოლოდ მას ან სისტემის ადმინისტრატორს
- **„საჭიროა მტკიცებულება“**: „შემოწმებაზე“ ფაილის გარეშე ვერ გადავა
- **„პროგრესი (%)“** — ავტომატური (3.3): დასრულებული = 100%; სხვა შემთხვევაში ქვედავალებების, საკონტროლო სიის და „ხელით პროგრესის“ საშუალო; თუ არცერთი არ არის — სტადიით (ახალი 0 / მიღებული 10 / მიმდინარე, შეჩერებული, დაბრუნებული 50 / შემოწმებაზე 90); „შემოწმებაზე“ მინიმუმ 90%. ჩანს ფორმაზე, ბარათზე, სიაში
- **თვისებების ისტორია** (3.8): დამატებითი ველების (პასუხისმგებელი, თარიღი, კატეგორია, ფილიალი, ხელით პროგრესი) ცვლილება ისტორიაში იწერება

ძველი მოდული `steelhouse_project` არ არის დაყენებული და აღარ გამოიყენება (მისი ნაწილი გადავიდა `steelhouse_task_flow`-ში).

## ქართული თარგმანი (`i18n/ka/`)

Odoo-ს ოფიციალური ქართული თარგმანი თითქმის ცარიელია, ამიტომ საჭირო აპები (მენიუები, Project, Employees, Discuss, To-do, ვებ-ინტერფეისი და სხვ.) ჩვენ ვთარგმნეთ — `i18n/ka/<module>.po` (ოფიციალური თარგმანები შენარჩუნებულია).

სერვერზე ჩადება: `sudo sh deploy/apply_ka_translations.sh <i18n/ka საქაღალდე>` → Odoo-ს გადატვირთვა → პარამეტრები → ენები → ქართული → განახლება (overwrite).
**Odoo-ს პაკეტის ყოველი განახლების შემდეგ ეს ხელახლა უნდა გაეშვას** (განახლება ფაილებს გადააწერს). ორიგინალები: `/var/backups/odoo/i18n_orig`.

ბაზაში ხელით ჩაწერილი თარგმანები — ქართულის ხელახალი ჩატვირთვა და ამ ჩასწორებების აღდგენა ერთად: `python deploy/reload_ka.py <admin პაროლი>`:
- `hr.hr_department_view_kanban` — „Employees“ → „თანამშრომელი“ (რიცხვის შემდეგ მხოლობითი; `hr.po`-ში იგივე ტექსტი მენიუსაც ეკუთვნის)
- `ir.model.constraint` `res_users_login_key` — დუბლირებული login-ის შეცდომა (იგივე `base.po`-შიცაა)
- `hr_holidays.hr_leave_view_form` — „A supporting document is required for this type of time off.“ (ოფიციალურ .pot-ში არ არის)
- `res.groups.privilege.placeholder` — „No“ → „არა“ (ველი არათარგმნადია; ახალი აპის დაყენების შემდეგ ხელახლა შესამოწმებელია)

## სისტემის პარამეტრები (გაკეთებულია)

- ენა: ქართული ყველა მომხმარებელზე და ახალ კონტაქტებზე (default)
- დროის სარტყელი: Asia/Tbilisi — სამუშაო გრაფიკები, თანამშრომლები, მომხმარებლები და ახალი კონტაქტები (default); დემოდან იყო Europe/Brussels
- თვითრეგისტრაცია გამორთულია (`auth_signup.invitation_scope = b2b`); პაროლის აღდგენა ჩართულია, მაგრამ ფოსტის (SMTP) გარეშე არ მუშაობს
- „ელფოსტით მარკეტინგი“, „გამოკითხვები“, „ბმულების ტრეკერი“, „ტესტები“ — მხოლოდ ადმინისტრატორს უჩანს
- 94 თანამშრომელს შექმნილი აქვს ანგარიში დროებითი პაროლით (login = სამუშაო ელფოსტა, ელფოსტის არქონისას — ტელეფონი). პაროლების ფაილი git-ში არ ინახება
