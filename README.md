# ფოლადის სახლი — დავალებების მართვის სისტემა

Odoo 19 Community-ზე (Project აპლიკაცია) აწყობილი დავალებების მართვის სისტემა.

- `Docs/ფუნქციონალი (2).docx` — კლიენტის მოთხოვნები
- `Docs/გეგმა.md` — დანერგვის გეგმა ეტაპებად და მოთხოვნების რუკა
- `addons/` — საკუთარი და OCA მოდულები (მომზადების პროცესშია)

პრინციპი: ჯერ Odoo-ს ჩაშენებული ფუნქციონალი, შემდეგ OCA მოდულები, საკუთარი კოდი — მხოლოდ ხარვეზებისთვის.

## მოდული `steelhouse_project` (ჯერ არ არის დაყენებული)

დაწერილია, სერვერზე არ არის დაყენებული — ელოდება დამტკიცებას (დავალებების ეტაპი).

დამოკიდებულება: მხოლოდ `project`. დაყენება: საქაღალდე `addons/` დაემატოს Odoo-ს `addons_path`-ში → Apps → Update Apps List → „Steelhouse Project“ → Install.

რას ამატებს:
- **სტადიები** და პროექტი „ოპერატიული დავალებები“: ახალი → მიღებული → მიმდინარე → შეჩერებული → შემოწმებაზე → დაბრუნებული → დასრულებული / გაუქმებული
- **ღილაკები** დავალებაზე: მიღება, დაწყება, შემოწმებაზე გაგზავნა, დადასტურება, დაბრუნება, შეჩერება, განახლება, ვადის გადაწევის მოთხოვნა, გაუქმება
- **მთავარი პასუხისმგებელი** და **შემმოწმებელი** (ნაგულისხმევად — ვინც დავალება შექმნა)
- **ვადის გადაწევა**: თანამშრომელი ითხოვს ახალ ვადას მიზეზით, შემმოწმებელი ადასტურებს/უარყოფს; თავდაპირველი ვადა ინახება. ვადას პირდაპირ ცვლის მხოლოდ შემმოწმებელი
- **დასრულება და გაუქმება** მხოლოდ შემმოწმებელს ან პროექტის მენეჯერს შეუძლია
- **მიზეზები**: დაბრუნება, შეჩერება (+ განახლების თარიღი), გაუქმება — ინახება და ჩანს ისტორიაში
- **მტკიცებულება**: თუ მონიშნულია, შემოწმებაზე გაგზავნა ფაილის გარეშე არ შეიძლება
- **შეხსენებები** (ყოველ საათში): ვადამდე 24 სთ — შემსრულებლებს; ვადაგადაცილება — შემმოწმებელს
- **ანგარიშებისთვის**: დასრულების თარიღი, დროულად შესრულდა / თავდაპირველ ვადაში შესრულდა, გადაწევებისა და დაბრუნებების რაოდენობა
- **შაბლონები**: „მარაგების დათვლა“, „მარაგის შევსების მოთხოვნა“

## მოდული `steelhouse_hr` (დაყენებულია, ვერსია 19.0.1.15.0)

დამოკიდებულება: `hr`, `hr_org_chart`, `web_hierarchy`, `hr_holidays`, `mail`.

რას ამატებს:
- დეპარტამენტზე **„ხელმძღვანელები“** (`manager_ids`) — რამდენიმე თანაბარი ხელმძღვანელი; Odoo-ს ერთი `manager_id` დამალულია და ავტომატურად ივსება სიის პირველით (საჭიროა თანამშრომლის `parent_id`-სთვის). **„შემცვლელი“** (`deputy_id`), **„ხელმძღვანელის პოზიცია“** (`sh_head_title`, ჩანს „ვაკანტური: …“-ით, როცა ხელმძღვანელი არ ჰყავს)
- თანამშრომელზე: **„ხელმძღვანელი“** (`sh_manager_ids`, ყველა თანაბარი ხელმძღვანელი — ფორმაში და სიაში მენეჯერის ნაცვლად), **„დამატებითი პოზიციები“** (`sh_extra_job_ids` — მეორე როლი სხვა დეპარტამენტში), ფილტრი **„ჩემი გუნდი“** ყველა თანაბარი ხელმძღვანელისთვის (`sh_my_team`; `hr.employee` და `hr.employee.public`)
- **ორგანიზაციული სქემა** თანამშრომლის ბარათზე (`controllers/org_chart.py` — `hr_org_chart`-ის კონტროლერის გადატვირთვა + შაბლონი `static/src/org_chart`): თანაბარი ხელმძღვანელები გვერდიგვერდ, ქვეშევრდომები და რაოდენობები ყველასთვის ერთნაირად
- **შვებულების მოთხოვნაზე ცხრილი „შემცვლელები“** (`steelhouse.leave.delegation`: დეპარტამენტი + შემცვლელი; მოთხოვნა 1.6). ხელმძღვანელს (მათ შორის თანაბარს) წინასწარ ევსება მის დეპარტამენტებზე; შემცვლელებს ეგზავნება შეტყობინება დამტკიცებისას/გაუქმებისას
- **დეპარტამენტების იერარქიის ხედი** (`js_class="steelhouse_department_hierarchy"`, `web.assets_backend_lazy`): კომპანიის ბარათი ცენტრშია; „გაშლისას“ ბარათის ქვეშ მუქ ჩარჩოში ჩანს დეპარტამენტის **პოზიციები** (`hr.job`, ქვეშ — ვინ იკავებს ან „ვაკანტური“) და ქვედეპარტამენტები; ჩადგმული ჩარჩო საჭიროებისას აფართოებს გარეს. ბარათზე რიცხვი = ყველა, ვინც ხელმძღვანელების ქვეშაა ქვედეპარტამენტების ჩათვლით (`sh_headcount`, დაჭერით — სია)

- **შვებულება:** „თანამშრომელი“ ასარჩევია „ახალი შვებულების“ ფანჯარაშიც (გადაწყვეტამდე); შემცვლელი ირჩევა მხოლოდ სტრიქონის დეპარტამენტის (ქვედეპარტამენტების ჩათვლით) თანამშრომლებიდან, სახელით; დეპარტამენტის შეცვლისას სხვა დეპარტამენტის შემცვლელი იშლება.
- **თანამშრომლების იერარქია** (`js_class="steelhouse_employee_hierarchy"`, `hr.employee` და `hr.employee.public`) — იგივე კომპონენტით, რაც დეპარტამენტებზე. აქტივობის დანიშვნის შეტყობინებაში ჩანს აქტივობის შენიშვნაც (`views/mail_templates.xml`) შემცვლელის შეტყობინება მიდის ელფოსტით და Odoo-ს ჩატშიც (OdooBot). შვებულების ფორმა ავტომატურად აღარ ინახება (გვერდის დახურვა/ჩანართის შეცვლა — `static/src/leave_no_autosave`). შვებულების მთავარ გვერდზე ბარათი **„ჩემთან დასამტკიცებელი“** (`hr.leave.sh_waiting_for_me_count`, მხოლოდ დამმტკიცებლებს)
- **შეტყობინებები:** მომხმარებელზე არჩევანი „ელფოსტით / Odoo-ში / ორივე“ (`sh_notification_channel`; „ორივე“ = Odoo-ს inbox + `sh_notify_email_too`, `mail.thread._notify_thread_by_email` გადატვირთვით). Push შეტყობინებების მოთხოვნა HTTP-ზე დამალულია (`static/src/push_prompt`)
- **აქტივობები:** შვებულების დამტკიცების ტიპები ხელით არჩევიდან დამალულია (`mail.activity.type.sh_system_only`); სხვისთვის დანიშნული აქტივობის შესრულებისას დამნიშნავს მიდის „✅ შეასრულა“; „შემოსულებში“ ღილაკი **„შესრულებულად მონიშვნა“** და „პასუხი“ ჩანს გარეთ (`static/src/message_actions`, 5 სწრაფი ღილაკი)
- **პასუხი ჩანაწერის გახსნის გარეშე:** ვინც ჩანაწერზე პირადად მიიღო შეტყობინება, შეუძლია უპასუხოს, ჩანაწერის ნახვის უფლების გარეშე (`controllers/thread.py`)

სტრუქტურა (PDF სქემა + `Docs/თანამშრომლების სია (1).xlsx`) აწყობილია სკრიპტებით `deploy/setup_structure.py`, `_2.py`, `_3.py` (წესი: სქემის ყუთი, რომლის ქვეშაც ხალხია → ქვედეპარტამენტი; ბოლო ყუთი → პოზიცია). სქემაში დასახელებული, სიაში არმყოფი ადამიანები შექმნილია ბარათებად ანგარიშის გარეშე.

შეზღუდვები:
- ამ ხედში ბარათის გადათრევა (drag & drop) გამორთულია — ზემდგომი დეპარტამენტი იცვლება ფორმიდან
- ერთ დონეზე ერთდროულად ერთი ბარათია გაშლილი (Odoo-ს სტანდარტული ქცევა)
- თანამშრომლის `parent_id` Odoo-ში ერთია (პირველი ხელმძღვანელი); შვებულების დამტკიცება ორივე ხელმძღვანელის მიერ — უფლებების ეტაპზე. თანამშრომლების იერარქიის ხედი ჯერ სტანდარტულია
- `res.users`-ზე ახალი ველის დამატებისას მოდული განახლდეს სერვერზე ბრძანებით (`odoo -u steelhouse_hr --stop-after-init`), არა RPC-ით: ველის სვეტის შექმნამდე შესვლა არ მუშაობს

სერვერზე: მოდულები დევს `/opt/odoo/custom-addons`-ში (`addons_path` — `/etc/odoo/odoo.conf`). ბაზის სარეზერვო ასლები: `/var/backups/odoo`.

## მოდული `steelhouse_task_flow` (დაყენებულია, ვერსია 19.0.1.6.0)

დამოკიდებულება: `project`, `hr`. მოთხოვნები 3.1, 3.3–3.9.
- სტადიას აქვს **„სტადიის ტიპი“** (`sh_kind`): ახალი / მიღებული / მიმდინარე / შეჩერებული / შემოწმებაზე / დაბრუნებული / დასრულებული / გაუქმებული. ახალი სტადიის დამატებისას ტიპი ფორმაში უნდა მიეთითოს
- სტადიის შეცვლისას სტატუსი თავისით მიჰყვება (დასრულებული → შესრულებული, გაუქმებული → გაუქმებული, დაბრუნებული → მოთხოვნილია ცვლილებები) და პირიქით
- **შეჩერება / დაბრუნება / გაუქმება** — მხოლოდ ღილაკით, სავალდებულო მიზეზით (შეჩერებისას + განახლების თარიღი); მიზეზი ინახება და ჩანს ისტორიაში
- **„შემმოწმებელი“** (ნაგულისხმევად შემქმნელი): დასრულება, დაბრუნება, გაუქმება — მხოლოდ მას ან სისტემის ადმინისტრატორს
- **„საჭიროა მტკიცებულება“**: „შემოწმებაზე“ ფაილის გარეშე ვერ გადავა
- **„პროგრესი (%)“** — ავტომატური (3.3): დასრულებული = 100%; სხვა შემთხვევაში ქვედავალებების, საკონტროლო სიის და „ხელით პროგრესის“ საშუალო; თუ არცერთი არ არის — სტადიით (ახალი 0 / მიღებული 10 / მიმდინარე, შეჩერებული, დაბრუნებული 50 / შემოწმებაზე 90); „შემოწმებაზე“ მინიმუმ 90%. ჩანს ფორმაზე, ბარათზე, სიაში
- **თვისებების ისტორია** (3.8): დამატებითი ველების (პასუხისმგებელი, თარიღი, კატეგორია, ფილიალი, ხელით პროგრესი) ცვლილება ისტორიაში იწერება

## ქართული თარგმანი (`i18n/ka/`)
